2. ENT-01 | Análisis y diseño del sistema
Vamos a definirlo como un conjunto de issues independientes, con descripción y criterios de aceptación para que puedas asignarlos directamente.
Entregable: diseño aprobado para iniciar desarrollo
EP-00 | Análisis y diseño de Norvia
Esta sería una épica transversal, no un módulo funcional de la plataforma.

Objetivo: establecer los requerimientos funcionales y técnicos, las reglas de negocio y los modelos necesarios para orientar la construcción de Norvia.
HU-001 | Definir el alcance funcional del sistema
Como equipo de desarrollo,
quiero definir el alcance funcional de Norvia,
para establecer qué funcionalidades se desarrollarán en el MVP y cuáles quedarán para futuras iteraciones.

Criterios de aceptación:
- Se identifican los módulos funcionales que conforman Norvia.
- Se define el propósito de cada módulo.
- Se identifican las funcionalidades principales de cada módulo.
- Se establece qué funcionalidades forman parte del MVP.
- Se identifican las funcionalidades que quedan fuera del alcance inicial.
- Se documentan las limitaciones y supuestos del proyecto.
- El alcance es revisado y aprobado por el equipo.
Entregable: documento de alcance funcional.
HU-002 | Identificar actores y perfiles de usuario
Como equipo de desarrollo,
quiero identificar los actores que interactuarán con Norvia,
para determinar sus necesidades y responsabilidades dentro del sistema.

Criterios de aceptación:
- Se identifican los actores que interactúan con la plataforma.
- Se describe el propósito de cada actor.
- Se diferencia entre usuarios internos de una empresa y usuarios administradores de la plataforma.
- Se identifican los perfiles organizacionales relacionados con el SG-SST.
- Se documentan las responsabilidades principales de cada perfil.
- Se diferencia el rol técnico del sistema de la responsabilidad organizacional dentro del SG-SST.
Actores iniciales propuestos:
- Administrador de plataforma.
- Administrador de empresa.
- Responsable de SST.
- Encargado de área.
- Trabajador.
- Integrante de Comisión Mixta.
- Auditor interno.
Entregable: catálogo de actores y perfiles.
HU-003 | Levantar requerimientos funcionales

HU-005 | Identificar y documentar reglas de negocio
Como equipo de desarrollo,
quiero documentar las reglas de negocio de Norvia,
para establecer las condiciones que controlarán las operaciones del sistema.

Criterios de aceptación:
- Cada regla tiene un identificador único.
- Las reglas están redactadas de manera clara y verificable.
- Se identifican las reglas relacionadas con la administración multiempresa.
- Se documentan las reglas de asignación de roles y responsabilidades.
- Se documentan las reglas principales de los módulos funcionales.
- Se identifican las restricciones de los datos.
- Las reglas se relacionan con los requerimientos funcionales correspondientes.
Ejemplos de reglas:
Código	Regla
RN-001	Cada empresa registrada debe tener un identificador único.
RN-002	Un usuario puede pertenecer a una o varias empresas.
RN-003	Un usuario puede tener diferentes roles en cada empresa.
RN-004	Los datos transaccionales deben pertenecer a una empresa.
RN-005	Un usuario no puede consultar información de otra empresa sin autorización.
RN-006	El EmpresaId de una operación se determina a partir del contexto autenticado.

Entregable: catálogo de reglas de negocio.

Entregable: backlog priorizado.

4. Cómo quedaría la relación con las épicas funcionales
No todas estas historias pertenecen a EP-01 Administración multiempresa. Son tareas transversales de análisis y diseño que preparan las distintas épicas.

Por eso, en GitHub usaría:
- Milestone: ENT-01 | Análisis y diseño del sistema.
- Epic/Project field: EP-00 | Análisis y diseño.
- Labels: analysis, design, database, architecture, api-contract.
Después, las historias funcionales como registrar empresa, autenticar usuario, configurar sector y diagnosticar riesgos se mantienen en sus respectivas épicas y se asignan al milestone de implementación correspondiente.

Mi recomendación: no comiencen ENT-02 hasta que estén aprobados, como mínimo, el alcance, el modelo de datos multiempresa, la estructura de arquitectura y los contratos iniciales de API. No necesitan documentar hasta el último detalle de los doce módulos para empezar, pero sí deben tener claras las decisiones que condicionan todo el backend.

Con esto queda definido el primer milestone. El siguiente paso lógico es construir ENT-02 con historias de usuario y criterios de aceptación técnicos, comenzando por la solución .NET, EF Core, entidades multiempresa, filtros globales y JWT.
